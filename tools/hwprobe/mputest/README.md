# MPUTEST - the MIDI-card probe

`MPUTEST.COM` tests a Roland MPU-401-family C-bus MIDI card (the MPU-PC98 or the MPU-PC98II),
and the core's model of the MPU-PC98II, from DOS. It finds the card and measures what a driver
sees. Then it plays labelled MIDI sequences that you can follow on a GS synth such as the SC-88
Pro. It also has a fixed byte-table mode (`/BYTES`) for a byte-exact check of the MIDI OUT line.

Run it on the core first, then on the real machine. Use the same binary on both: the capture
header carries the CRC-32 of the op tables, and the decoder refuses a capture from a different
build.

## Files

| file | what |
|---|---|
| `mputest.s` | the program (GNU as, `make -C tools/hwprobe mputest/mputest.com`) |
| `mputest_decode.py` | owns the op tables, the reference wire model and the capture decoder |
| `mputest_tables.inc` | GENERATED by `mputest_decode.py --gen`: the op scripts the program runs |
| `../../../tests/pc9821/mputest_bytes.svh` | GENERATED: the `/BYTES` script and its expected wire stream, for `tb_pc9821_mpu_probe` |
| `RUNMPU.BAT` | `RUNMPU` writes `MPUTEST.TXT`; `RUNMPU BYTES` writes `MPUBYTES.TXT` |

`python3 tools/hwprobe/mputest/mputest_decode.py --selftest` checks that the two generated files
are current, checks the reference model, and checks the decoder's own failure paths. The build
refuses to run if an include is stale.

## Usage

```
MPUTEST [/BYTES] [/RAW[:n]] [/NOPLAY] [/NOIRQ] [/P:hhhh] [/O:file]
```

| option | sections run |
|---|---|
| (none) | DETECT, RESET (with the IRQ check), UART (the FIFO measurement), PLAY, EXIT |
| `/BYTES` | DETECT, then only the `/BYTES` table; nothing else reaches the MIDI line |
| `/RAW[:n]` | adds RAW: an n-byte SysEx (default 200, range 4..4000) written blind, with no BUSY poll, after UART mode has settled for 100 ms. This is labelled loss behaviour, so compare the wire capture |
| `/NOPLAY`, `/NOIRQ` | skip the music, or skip the IRQ check |
| `/P:hhhh` | the card's base (the data port; status and command are at base+2). Without it, the scan picks E0D0, or the only window that answers |
| `/O:file` | the capture file (default `MPUTEST.TXT`). Everything also goes to the screen |

Press ESC during a pause to skip the rest of the current script (an `ABORT` row) and go straight
to the closing reset.

Run it from plain DOS with no MIDI driver resident. It needs no memory manager.

## What it measures (the capture rows)

The capture writes `BEGIN:x` / `END:x` around each section, so a hang shows as a BEGIN with no
END. `MPUTEST DONE` is always the last line.

- **DETECT** - `PORT base=hhhh st=ss dat=dd` for each of the 16 option windows
  `0xC0D0 + k*0x400`. It reads the status port, and reads the data port only if the status is
  not open bus (FF). Then `FOUND base=` or `NOTFOUND`.
- **CMD** - `CMD <sec> cc ack=FE polls= t= extra= busy=` for every command. `t` is the ACK
  latency in ARTIC ticks (3.255 us each), measured from the command write to status bit 7
  clearing. `polls` counts status reads. `extra` counts further bytes that were waiting; on a
  real card these are MIDI IN data. `busy` counts BUSY polls before the write. `ack=--` means
  no answer within 100 ms.
- **IRQ** - `IRQ imr= before= pend= after= ack=`. Each field is a 16-bit {slave,master} 8259
  word. The check runs with IF=0 and both IMRs at 0xFF: it reads the IRR, writes 0x94
  (clock-to-host off, which is ACK only), reads the IRR with the ACK pending, reads the ACK,
  then reads the IRR again. A bit that is set in `pend` but not in `before` is the card's
  line, and `after` shows whether the request is held or withdrawn. The as-found masks are
  restored.
- **FIFO** - 200 bytes of a non-commercial (ID 7D) SysEx, written in UART mode with BUSY polled.
  The row records `first_busy` (the index of the first write that met BUSY: how many bytes the
  card takes back to back), the total BUSY polls, the time (320 us per byte is the 31250-baud
  line), and timeouts. The `FIFOST` rows give the status after each of the first 48 writes.
- **RAWW** - the blind burst: the bytes written, the time taken, and the status afterwards.
  Which bytes survived only shows in a wire capture.
- **LABEL** - printed before each audible sequence.

## The audible sequences (PLAY, about 75 s)

The program prints a label before each sequence and leaves a gap after it.

1. UART mode (0x3F).
2. GS reset `F0 41 10 42 12 40 00 7F 00 41 F7` (SC-88 Pro manual p.191).
3. The Sound Canvas display text "PC-9821 MPUTEST  MIDI probe", sent as
   `F0 41 10 45 12 10 00 00 <ASCII> sum F7`: model 45H, address 10 00 00, 1..32 characters,
   scrolling past 16 (SC-88 Pro manual pp.190-207).
4. A C major scale on channel 1, piano.
5. Four chords on channels 1-4, with program changes to piano, strings, trumpet and nylon
   guitar.
6. A running-status run: 16 notes on channel 1 under a single 0x90.
7. Drums on channel 10.
8. A 300-byte SysEx with ID 7D, then one note to show the synth is still alive.
9. A pitch-bend sweep on channel 1 (strings): up, down, and back to centre.
10. All notes off and reset controllers on channels 1-16.
11. Leave UART mode (0xFF).
12. Intelligent mode: a 0xD0 note-on, then a 0xD0 running-status note-off.
13. Intelligent mode: a 0xDF SysEx, the display text "MPUTEST done".

Each message's checksum is computed by the Roland rule: (address + data + sum) is a multiple of
128 (SC-88 Pro manual p.207).

## /BYTES: the fixed sequence (stage A)

| step | sent | NP2kai wire (`np2` and `manual` models) |
|---|---|---|
| 1 | command FF | 16 x `Bn 7B 00` |
| 2 | command 3F | 16 x `Bn 7B 00` |
| 3 | GS reset (11 bytes) | as sent |
| 4 | `C0 00 90 3C 40 3E 40 40 40 3C 00 3E 00 40 00` (running status) | as sent |
| 5 | `F0 7D 00 01 .. 7F 00 .. 08 F7` (140 bytes) | as sent |
| 6 | `E0 00 40 B0 7B 00` | as sent |
| 7 | command FF (in UART mode) | nothing (no ACK either, except in the `np2` model) |
| 8 | `D0`, `91 3C 40`, `D0`, `3C 00` | `91 3C 40 91 3C 00` |
| 9 | `DF`, `F0 7D 01 02 03 F7` | as sent |
| 10 | command FF | 16 x `Bn 7B 00` |

`mputest_decode.py --expect BYTES --out WIRE.BIN` writes the expected 328 bytes. The `quiet`
model is the same stream without the three resets' bursts: that is what a card produces if
its resets send nothing.

## Behaviours expected to differ (core / MPU-PC98II / MPU-PC98)

The core follows NP2kai `cbus/mpu98ii.c` except at one point. The Roland MPU-401 Technical
Reference Manual (v1.5A,
https://www.shot.org/mirrors/misc/mindcandydvd.com/pub/drivers/Roland/MPU-401%20technical%20reference%20manual.pdf)
differs from NP2kai on that point and is silent on another:

- **0xFF leaving UART mode.** The manual says "The MPU-401 will not return an ACK ($FE) in this
  one case." NP2kai ACKs it (`mpu98.mode = 0; setrecvdata(MPUMSG_ACK);`). The core follows the
  manual and does not (todo item 173, an owner decision): DOSBox-X does not ACK it either, and
  the owner's MPU-PC98 did not in 4 of 4 runs (`docs/probes/MPUTEST-XE10.TXT`,
  `MPUTEST-XE10-BYTES.TXT`). MPUTEST waits at most 100 ms and records `ack=--` if nothing comes.
  The decoder checks the CMD rows against the `manual` model and notes NP2kai's answer beside
  the rows where it differs.
- **All-notes-off on 0xFF / 0x3F.** NP2kai's `sendmpureset` puts 16 x `Bn 7B 00` on MIDI OUT for
  both commands, and the core copies it. The manual mentions no MIDI OUT bytes for either.
  DOSBox-X sends none. Neither emulator is evidence of what the hardware does; the `/BYTES`
  capture of a real card decides it (the decoder reports `manual` or `quiet`; `manual` has
  NP2kai's wire, byte for byte, and the `np2` model can still be named with `--model np2`).
- **Things a real card has that the core does not:** an ACK latency (the card's own CPU), a
  per-byte DRR busy time, MIDI IN (which shows as `extra=`), and a finite UART-mode loss
  pattern under `/RAW`.

The two Roland cards (research notes; no Roland document for the original MPU-PC98 was found):

| | MPU-PC98 (original) | MPU-PC98II |
|---|---|---|
| I/O base | fixed E0D0/E0D2 | 16 bases C0D0..FCD0 (0x400 steps) by DIP switch, default E0D0 |
| IRQ | fixed INT2 (IRQ6) | INT0/1/2/5 (IRQ3/5/6/12) by jumper, default INT2 |
| other | tape sync, ¥38,000 (1991) | no tape sync, ¥19,800, pull-out knob |
| reported issues | "80286以降だと不具合が発生するかもしれない" (may misbehave on 80286 and later); a Roland FAQ, quoted second-hand, says faster PCs may not detect it or may mishandle data; a PC-9821Xs froze in VIPER V16 tens of seconds into the music | described as the improved successor; a "bug-fix version" claim is hearsay |
| UART mode (0x3F) | no source says it is missing; the manual records UART mode before ROM v1.3. This card's ROM revision is unknown | yes |

Sources:
- https://www.soundoffice.com/soc10th/MPU-PC98II.php (II bases, INT jumper, default)
- https://j02.nobody.jp/jto98/n_desk_midi/sc88.htm (original fixed, 80286 remark)
- https://gonta-house.hatenablog.com/entry/9971148 (original: INT2/E0D0 fixed, Roland FAQ quote, VIPER V16 freeze)
- https://pokug.net/entry/2022/07/15/191019 (original fixed, II by DIP, "bug-fix" hearsay)
- https://kizuna.5ch.io/test/read.cgi/i4004/1728577019/691-704 (tape sync, knob, games hard-code E0D0/INT2)
- https://www.roland.com/jp/lp/catalog_museum/pdf/NAM-1397.pdf (Roland 1991 catalogue: prices, tape sync)
- https://static.roland.com/assets/media/pdf/SC-88PRO_OM.pdf (SC-88 Pro SysEx, display text, checksum)

The found base and IRQ go in `FOUND base=` and the `IRQ` row. On the original card they should
read E0D0 and IRQ6.

## Decoding

```
python3 tools/hwprobe/mputest/mputest_decode.py MPUTEST.TXT                  # summary + integrity
python3 tools/hwprobe/mputest/mputest_decode.py MPUBYTES.TXT --wire WIRE.BIN  # vs the wire capture
python3 tools/hwprobe/mputest/mputest_decode.py CORE.TXT --pair XE10.TXT      # both summaries
```

`--wire` compares byte for byte first, then message by message. The message-level comparison
covers capture paths that re-frame the stream: USB-MIDI and NP2kai's own MIDI-OUT file re-insert
running status, and `amidi -r` drops 0xFE/0xF8 unless given `-a -c`. It tries both models and
says which one the capture matches. For `/RAW` it also counts the 7D SysEx bytes that survived.

**Reference run.** NP2kai, with its MPU-PC98II at E0D0/INT2 and MIDI OUT sent to a file
(`.build/mputest/np2/`, not committed), runs this binary to `MPUTEST DONE`. On both `/BYTES` and
the default flow with `/RAW`, it matches the `np2` model message for message, and it reports
IRQ6, withdrawn after the ACK read.
